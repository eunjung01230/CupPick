# Review Brief

팀원이 발견한 문제를, **수정을 맡을 사람이 빠르게 인지할 수 있는 형태**로 재구성한다.

## 이 스킬이 해결하는 것

바이브 코딩 팀에서 리뷰는 대부분 자연어로 온다. 리뷰어는 문제를 발견한 순간의 사고 흐름을 그대로 쓴다 — 어디서 발견했는지, 왜 그렇게 생각했는지, 아마 이럴 것 같다는 추측까지 뒤섞인다. 내용 자체는 정확한데도 받는 사람이 못 알아듣는다.

원인은 두 가지다.

1. **불일치가 산문으로 서술돼 있다.** "A 문서에는 이렇게 돼 있는데 B 문서는 좀 다르고 C도 예전 거예요"를 읽으면, 독자는 세 문서의 내용을 머릿속에 동시에 띄워놓고 비교해야 한다. 이게 느리다. 나란히 배치하면 즉시 보인다.
2. **결론과 추측이 섞여 있다.** "아마 중간에 바뀐 게 반영 안 된 것 같은데"는 확정 사실이 아니다. 독자는 어디까지가 확인된 사실이고 어디부터가 리뷰어의 짐작인지 구분하지 못한 채 작업에 들어간다.

따라서 이 스킬의 일은 **정보를 추가하는 게 아니라 배치를 바꾸고 확실성 수준을 표시하는 것**이다.

## 워크플로우

### 1단계: 이슈 단위로 분리

리뷰 글 하나에 별개의 문제가 여러 개 들어 있는 경우가 많다. **원인이 다르면 다른 이슈**다.

- 같은 원인에서 파생된 여러 증상은 하나의 이슈로 묶는다. 예: "온보딩 3단계 → 2단계 변경 미반영" 때문에 스펙·화면정의서·데이터모델·README가 전부 어긋난 것은 **이슈 1개**이고 영향 문서가 4개다. 이걸 4개 이슈로 쪼개면 받는 사람은 근본 원인을 못 본다.
- 반대로 원인이 다르면 분리한다. 표기 오류와 논리 충돌은 같은 글에 있어도 별개다.

이슈가 하나면 굳이 번호를 매기지 않는다. 구조가 내용보다 무거워지면 인지 속도가 오히려 떨어진다.

### 2단계: 실제 문서로 근거 확인

리뷰어가 지목한 파일에 접근할 수 있으면 **직접 열어서 대조한다.** 이게 브리핑의 신뢰도를 결정한다.

- 리뷰어의 지적이 맞는지 확인한다. 자연어 리뷰는 기억에 의존해 쓰이는 경우가 많아, 리뷰어가 오해했거나 이미 수정된 내용을 지적하는 일이 실제로 발생한다.
- 리뷰어가 언급하지 않은 연관 문서도 같은 불일치를 갖고 있는지 확인한다. 리뷰어가 "아마 README도 예전 거예요"라고 흐리게 말한 부분을 확정해주면 작업 범위가 명확해진다.
- 확인한 내용은 정확한 인용 위치(파일명 + 섹션/줄)와 함께 쓴다.

파일에 접근할 수 없으면 확인하지 않았다는 사실을 명시한다. 절대 확인한 것처럼 쓰지 않는다.

### 3단계: 확실성 수준으로 나누기

각 정보를 세 층으로 분리한다. 이 구분이 이 스킬의 핵심 가치다.

| 표시 | 의미 |
|---|---|
| **확인됨** | 실제 문서를 열어 대조한 사실 |
| **리뷰어 주장** | 리뷰어가 단정했지만 아직 미확인 |
| **추측** | 리뷰어가 "아마", "~같은데"로 말한 부분 |

추측을 확인됨처럼 쓰면 받는 사람이 그걸 전제로 Claude에게 작업을 지시하고, 잘못된 수정이 문서에 퍼진다. 자연어 리뷰가 모호할수록 이 구분을 더 엄격히 지킨다.

### 4단계: 판단이 필요한 지점 분리

문서 불일치는 대부분 "어느 쪽이 맞는지"를 사람이 결정해야 풀린다. 이건 수정 작업이 아니라 **의사결정**이다.

- 어느 쪽이 최신/정답인지 리뷰 글에서 확정할 수 없으면, 임의로 정하지 말고 선택지를 제시하고 누가 결정해야 하는지 적는다.
- 리뷰어가 이미 답을 알고 있는데 명시만 안 했을 가능성이 높으면 "리뷰어에게 한 줄 확인"으로 안내한다. 이게 잘못 수정하고 되돌리는 것보다 훨씬 빠르다.

### 5단계: 위임용 지시문 만들기

받는 사람은 이 내용을 Claude에게 넘겨 실제 수정을 맡긴다. 그대로 복사해 붙일 수 있는 지시문을 마지막에 붙인다.

- 결정이 끝난 부분만 지시문에 넣는다. 미결정 항목은 지시문에 넣지 말고 "결정 후 추가"로 표시한다.
- 수정 대상 파일과 바꿀 내용을 구체적으로 쓴다.

## 출력 템플릿

이슈가 하나일 때의 기본형이다. 여러 개면 `## 이슈 1`, `## 이슈 2`로 감싼다.

```markdown
## 한 줄로

[문제의 핵심. 원인까지 한 문장에 담는다]

## 무엇이 어긋났나

| 문서 | 뭐라고 되어 있나 | 상태 |
|---|---|---|
| `docs/spec.md` (3장) | 온보딩 3단계 | 옛 내용 |
| `docs/screen.md` | 온보딩 2단계 | 최신으로 추정 |
| `docs/model.md` | `step` 값 1·2·3 | 3단계 기준 |

**원인:** 2단계로 줄이는 변경이 일부 문서에만 반영됨

## 이대로 두면

[실제로 벌어질 일. 한두 줄. 추상적 서술 금지]

## 확실성

- **확인됨:** [실제 파일 대조한 내용]
- **리뷰어 주장(미확인):** [있으면]
- **추측:** [리뷰어가 "아마"로 말한 부분]

## 먼저 정할 것

- [ ] 2단계가 최종인지 확인 — 리뷰어 또는 기획 담당
- (결정되면 나머지는 문서 수정만 남음)

## Claude에게 넘길 지시문

```
[복사해서 바로 쓸 수 있는 프롬프트]
```
```

섹션은 필요한 것만 쓴다. 추측이 없으면 `확실성` 섹션을 지우고, 결정할 게 없으면 `먼저 정할 것`을 지운다. 빈 섹션을 남기면 읽는 사람이 훑어야 할 양만 늘어난다.

## 지켜야 할 것

**원문에 없는 내용을 만들지 않는다.** 리뷰어가 "좀 이상한데요"라고만 썼다면 어떻게 이상한지 추론해 단정하지 말고, 문서를 직접 확인해 채우거나 `확인 필요`로 남긴다. 근거를 만들어내면 받는 사람은 그걸 그대로 Claude에게 지시하고, 문제는 조용히 확대된다.

**분량을 줄이는 게 목적이 아니라 인지 속도를 높이는 게 목적이다.** 짧게 만들려고 지적을 빠뜨리면 실패다. 표가 산문보다 길어져도 읽는 시간이 짧아지면 그게 맞는 선택이다.

**용어를 풀어쓴다.** 팀의 코드 지식 수준이 높지 않다는 전제로 쓴다. 원문에 기술 용어가 있으면 짧은 괄호 설명을 붙이고, 없던 용어를 새로 들여오지 않는다. `순환 참조가 발생합니다` 대신 `A가 B를 참조하고 B가 다시 A를 참조해서 무한히 돌게 됩니다`.

**리뷰어를 평가하지 않는다.** 리뷰 글이 산만했다거나 리뷰어가 잘못 짚었다는 식의 논평은 쓰지 않는다. 리뷰어의 지적이 사실과 다르면 `확인 결과 현재 문서에는 이미 반영되어 있음`처럼 사실만 적는다.

## 예시

**입력 (팀원이 슬랙에 쓴 글):**
> 제가 기획 문서 보다가 좀 이상한 걸 발견했는데요, 우리 처음에 온보딩 3단계로 하기로 했었잖아요? 근데 spec 문서엔 그대로 3단계로 적혀 있는데 화면 정의서엔 2단계로 줄어든 버전이 그려져 있어요. 아마 중간에 논의했던 게 반영된 것 같은데 spec은 안 고친 것 같고… 그리고 데이터 모델 문서에 onboarding_step 필드가 3단계 기준으로 1,2,3으로 정의되어 있어서 이것도 같이 봐야 할 것 같아요. 아 그리고 README에 있는 플로우 설명도 예전 거예요 아마.

**출력:**
```markdown
## 한 줄로

온보딩을 3단계 → 2단계로 줄인 변경이 화면 정의서에만 반영되고 나머지 문서 3개는 옛 내용으로 남아 있습니다.

## 무엇이 어긋났나

| 문서 | 뭐라고 되어 있나 | 상태 |
|---|---|---|
| `docs/screen.md` | 온보딩 2단계 | 최신 (추정) |
| `docs/spec.md` | 온보딩 3단계 | 옛 내용 |
| `docs/model.md` | `onboarding_step` = 1·2·3 | 옛 내용, 값 범위 수정 필요 |
| `README.md` | 플로우 설명 | 옛 내용 (미확인) |

**원인:** 단계 축소 변경이 화면 정의서에만 반영됨

## 이대로 두면

Claude에게 온보딩 관련 작업을 맡길 때 어느 문서를 읽느냐에 따라 3단계로 구현하거나 2단계로 구현합니다. 특히 `onboarding_step`은 값이 3까지 정의되어 있어서, 2단계 기준으로 만든 화면과 맞지 않는 데이터가 저장될 수 있습니다.

## 확실성

- **확인됨:** `spec.md` 3단계, `screen.md` 2단계, `model.md` 값 1·2·3 — 파일 대조 완료
- **추측:** 2단계가 최신이라는 것, `README.md`가 옛 내용이라는 것 — 둘 다 리뷰어가 "아마"로 말한 부분

## 먼저 정할 것

- [ ] **2단계가 최종 맞는지 확인** — 리뷰어 또는 기획 담당에게 한 줄 물어보면 끝납니다. 이게 정해지지 않으면 나머지 수정 방향이 전부 뒤집힙니다.

## Claude에게 넘길 지시문

(위 확인이 끝난 뒤 사용)

```
온보딩 플로우가 3단계에서 2단계로 변경되었으나 일부 문서에 반영되지 않았습니다.
docs/screen.md 의 2단계 플로우를 기준으로 아래를 수정해주세요.

1. docs/spec.md — 3단계 기준 서술을 2단계로 수정
2. docs/model.md — onboarding_step 필드의 값 범위를 1·2로 수정
3. README.md — 플로우 설명 확인 후 2단계 기준으로 갱신

수정 전에 각 파일에서 실제로 바꿀 부분을 먼저 보여주세요.
```
```

## 엣지 케이스

- **리뷰 글이 이미 짧고 명확하다**: 억지로 표를 만들지 않는다. 그 사실을 말하고, 부족한 것(정확한 파일 위치, 판단 필요 지점)만 채운다.
- **리뷰어의 지적이 사실과 다르다**: 확인 결과를 `확실성` 섹션 맨 위에 적는다. 예: `확인 결과 model.md는 이미 2단계로 수정되어 있음 — 이 항목은 작업 불필요`. 받는 사람이 헛일을 하지 않게 하는 게 가장 큰 절약이다.
- **리뷰 글에 문제 제기와 제안이 섞여 있다**: 문제(사실)와 제안(리뷰어 의견)을 분리한다. 제안은 `먼저 정할 것`의 선택지로 넣는다.
- **불일치가 문서가 아니라 문서와 실제 구현 사이에 있다**: 표의 `문서` 열에 `실제 구현 (파일명)`을 한 행으로 넣고 같은 구조를 쓴다.
- **이슈가 5개 이상이다**: 맨 위에 이슈 목록만 먼저 나열하고, 각 이슈 상세를 그 아래에 둔다. 받는 사람이 전체 규모를 먼저 파악해야 어디서부터 손댈지 정할 수 있다.
